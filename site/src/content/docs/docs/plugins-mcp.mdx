telos includes extension points for plugins and MCP so tool ecosystems can be registered with the same runtime used by sessions and the CLI.

## Plugins

The runtime API exposes `PluginRegistry`, `PluginId`, `PluginError`, and `BUILTIN_MARKETPLACE`. Plugins can load tool specs, lifecycle policies, skills, prompt sections, output styles, settings, user configuration, MCP and LSP declarations, and subagents.

Marketplace metadata is represented by `BUILTIN_MARKETPLACE` and plugin registry data. Use it to describe available plugin entries rather than hard-coding extension behavior in a client.

The legacy `hooks` and `interceptors` manifest fields are rejected. Use semantic lifecycle policies instead:

```json
{
  "manifestVersion": 2,
  "name": "guardrails",
  "version": "1.0.0",
  "policies": {
    "sessionStart": [
      {
        "name": "load-context",
        "mode": "create",
        "command": "./bin/session-policy",
        "timeout": 30000
      }
    ],
    "modelBeforeRequest": [
      {
        "name": "request-audit",
        "command": "./bin/request-policy"
      }
    ],
    "toolBeforeInvoke": [
      {
        "name": "shell-guard",
        "matcher": "Bash*",
        "command": "./bin/tool-policy"
      }
    ]
  }
}
```

Plugin manifests may declare all eight semantic points: `sessionStart`, `sessionEnd`, `turnStart`, `modelBeforeRequest`, `modelResponse`, `toolBeforeInvoke`, `toolAfterInvoke`, and `turnBeforeFinish`. `sessionStart` may filter `create` versus `resume`; the two tool points may use a glob `matcher`.

Policy commands run with the plugin directory as their working directory. They receive a tagged `PolicyContext` JSON object on stdin and must write exactly one outcome object to stdout:

```json
{"decision":"continue","feedback":["optional model feedback"]}
```

To reject an operation, return `{"decision":"reject","reason":"explanation"}`. Policy process failures and policy rejections are emitted as distinct `PolicyFailed` and `PolicyRejected` events. Provider retry/failure, compaction, persistence, and session close are observer events rather than command policies. Output is bounded to 1 MiB, and invalid matchers, empty commands, or zero timeouts fail manifest validation.

### Manifest contract

`plugin.json` is a strict, camel-case manifest. `manifestVersion` must be `2`; v1, omitted versions, and unknown fields are rejected. Plugin and marketplace entry versions use semver, must be present, and must match exactly. Component paths remain under the plugin root, and installed directory names use `<name>@<marketplace>`.

```json
{
  "manifestVersion": 2,
  "name": "typescript-assist",
  "version": "1.2.0",
  "dependencies": [
    { "name": "language-core", "version": "^2.1" },
    { "name": "shared-rules", "marketplace": "official", "version": ">=1.4, <2" }
  ],
  "tools": ["./tools/format.json"],
  "outputStyles": ["./styles/concise.md"],
  "lspServers": {
    "typescript": {
      "command": "typescript-language-server",
      "args": ["--stdio"],
      "extensionToLanguage": { ".ts": "typescript" }
    }
  },
  "userConfig": {
    "endpoint": {
      "type": "string",
      "title": "Endpoint",
      "description": "Service endpoint",
      "required": true
    },
    "token": {
      "type": "string",
      "title": "Token",
      "description": "Service token",
      "sensitive": true
    }
  }
}
```

Output styles accept Markdown/plain text or JSON containing an `instructions` string. They become static prompt sections. LSP servers become read-only namespaced tools supporting hover, definition, references, document symbols, and diagnostics over stdio. The bridge answers standard configuration, capability-registration, progress, and workspace requests while rejecting workspace edits. Plugin tool, policy, LSP, and MCP subprocesses receive a minimal platform environment plus declared plugin configuration; the agent/provider environment is not inherited.

Configuration is validated by type, required fields, numeric bounds, file/directory existence, and unique environment-variable projection. It is stored per project in `.telos/plugins/plugin_config.json` with owner-only permissions on Unix. Configuration updates merge with stored values so omitted sensitive fields are preserved; use `clear-config` to remove all user configuration. Sensitive values are redacted from inspection and prompt interpolation. Use `${CONFIG:key}` only for non-sensitive prompt values; subprocesses receive `TELOS_PLUGIN_CONFIG` and normalized `TELOS_PLUGIN_<KEY>` variables. The key `config` and keys that normalize to the same environment name are rejected.

Runtime component names include the marketplace to avoid collisions. Tools use `plugin__<name>__<marketplace>__<tool>`, and plugin subagents use `<name>@<marketplace>:<agent>`.

### Management

Plugins and marketplaces can be managed without starting a model provider:

```bash
telos plugin marketplace-add-local ./marketplace
telos plugin marketplace-refresh my-marketplace
telos plugin marketplace-search formatter
telos plugin marketplace-list-plugins --name my-marketplace
telos plugin install formatter@my-marketplace
telos plugin config formatter@my-marketplace --json '{"mode":"strict"}'
telos plugin enable formatter@my-marketplace
telos plugin inspect formatter@my-marketplace
telos plugin upgrade formatter@my-marketplace
telos plugin disable formatter@my-marketplace
telos plugin uninstall formatter@my-marketplace
telos plugin marketplace-remove my-marketplace
```

Install and upgrade refresh the selected marketplace and keep an installed dependency when its version already satisfies the requested range. Otherwise, the current catalog version is considered as its replacement. Existing configuration is validated before replacement, and all affected directories are switched as one rollback-aware batch. A catalog/plugin version mismatch, an unsatisfied semver range, or an active plugin that would need replacement aborts the operation and preserves every previous version. Disable a plugin before upgrading it.

Marketplace refresh only updates catalog metadata. When an entry disappears, every installed copy is retained and reported as orphaned; removal is always an explicit uninstall operation. A marketplace cannot be removed while any of its plugins remain installed.

Marketplace sources support local directories, inline catalogs, GitHub/git, direct JSON URLs, and npm catalogs; plugin entries support local, GitHub/git, npm, and pip sources. npm lifecycle scripts are disabled during installation. Source declarations currently define the trust boundary: Git SHA pinning is optional and npm/pip checksums or signatures are not verified, so only register trusted marketplaces and pin immutable sources where possible. The desktop settings dialog lists registered marketplace entries and supports install, upgrade, disable, uninstall, schema inspection, and configuration with sensitive-value preservation.

Migration note: manifest v1 is intentionally unsupported. Set `manifestVersion` to `2`, add a required semver `version`, convert every dependency string into the versioned object form above, and move removed `hooks` or `interceptors` commands to `policies`. Marketplace manifests must remove the obsolete `forceRemoveDeletedPlugins` field. Unknown or misspelled fields fail validation.

## Skills

The skill system uses Markdown skill files with YAML frontmatter. Loaded skills can be injected into prompts so an agent has specialized workflow or domain instructions available during a turn.

## MCP Tool Bridge

`McpManager`, `McpClient`, and `McpToolBridge` connect MCP servers to the tool registry over stdio JSON-RPC.

MCP tools are registered with bridge names in this shape:

```text
mcp__<server>__<tool>
```

Once bridged, MCP tools participate in the same tool execution and approval flow as other registered tools.
